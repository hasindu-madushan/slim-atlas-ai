## Root cause

A single shared MCP SDK `Server` instance (`this.server`, created once in the constructor at `src/server.ts:91`) is reused across every HTTP client. The SDK's `Protocol` base only allows **one transport at a time**, so the 2nd client triggers `await this.server.connect(newTransport)` at `src/server.ts:606` → *"Already connected to a transport."* The `httpTransports` Map tried to multiplex transports, but one `Server` can only own one transport. The stdio path is unaffected (single connection).

Key insight: the request handlers in `setupHandlers` close over `this` (the `PuppeteerMCPServer`: `sessionManager`, `sessionQueues`, etc.), **not** over the `Server` instance. So registering the same handlers on multiple per-connection `Server` instances is safe — they all route to the shared browser session pool. This matches the MCP SDK's official streamable-HTTP example.

## Fix — one `Server` per connection (in `src/server.ts`)

**1. Remove the shared `Server` field** (delete line 81 `private server: Server;`). It's only referenced in the constructor, `setupHandlers`, and the stdio connect — all of which are refactored below.

**2. Make `setupHandlers` take the server as a param** (`private setupHandlers(server: Server): void`), and register `ListToolsRequestSchema` / `CallToolRequestSchema` handlers on the passed-in server. Handler bodies unchanged (they close over `this`).

**3. Add a factory method:**
```ts
private createServer(): Server {
  const server = new Server(
    { name: 'slimatlas', version: '1.0.0' },
    { capabilities: { tools: {} } },
  );
  this.setupHandlers(server);
  return server;
}
```

**4. Simplify the constructor** — drop the `this.server = new Server(...)` and `this.setupHandlers()` lines (keep `startCleanupJob()` and the existing logging).

**5. Track per-connection `{ server, transport }`** — change the Map type:
```ts
private httpTransports: Map<string, { server: Server; transport: StreamableHTTPServerTransport }> = new Map();
```

**6. `run()` stdio path** — build its own server:
```ts
const server = this.createServer();
const stdio = new StdioServerTransport();
await server.connect(stdio);
```

**7. `runHttp()` request handler:**
- `existing` lookup returns the pair; use `existing.transport.handleRequest(...)` / `existing.transport.close()`.
- New-connection branch:
```ts
const server = this.createServer();
const newTransport = new StreamableHTTPServerTransport({
  sessionIdGenerator: () => randomUUID(),
  onsessioninitialized: (id) => {
    this.httpTransports.set(id, { server, transport: newTransport });
    log.info('server', `HTTP session ${id} initialized`);
  },
  onsessionclosed: (id) => {
    this.httpTransports.delete(id);
    log.info('server', `HTTP session ${id} closed`);
  },
});
newTransport.onerror = (err) => { log.error('server', `HTTP transport error: ${err.message}`); };
await server.connect(newTransport);   // each connection gets its own Server — no more "Already connected"
await newTransport.handleRequest(req, res, parsedBody);
```
- DELETE branch uses `existing.transport.close()`.

**8. `shutdown()`** — iterate pairs and close `entry.transport` (closing the transport disconnects its owning `Server`; the `Server` is then GC-able). No other change needed.

## Why this is minimal & correct
- Two simultaneous brand-new clients each build their own `Server`+`transport` and `connect` independently → no contention.
- Handlers route through the single shared `sessionManager`/`sessionQueues`, so all clients share browser sessions exactly as today (per-session serialisation still holds).
- Stdio behavior is identical (one server, one connect).
